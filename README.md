# Dev Helper

Chrome-расширение (Manifest V3) — набор небольших помощников для повседневной работы разработчика.
Каждый помощник — отдельная фича со своим разделом настроек и переключателем «Включено».

| Фича | Что делает |
| --- | --- |
| [Merge requests](#фича-merge-requests) | копирует название и ссылку MR, открывает топик в Telegram и задачу в Jira, префиксы `blocking:` / `nit:` в комментариях |
| [Задачи Jira](#фича-задачи-jira) | блок в задаче: «Залить на stage» — MR из задачи и форма MR на stage; «Pipeline ветки» — последний pipeline ветки MR для preview |
| [Релизы Jira](#фича-релизы-jira) | фильтр по меткам над списком задач релиза («без меток», «без обязательных меток», исключение, «ИЛИ / И»), метки и MR в строках, копирование задач, ссылка на поиск Jira |
| [Переходы](#фича-переходы) | переход с текущей страницы на связанную по шаблону адреса (например, с товара в админку) — из контекстного меню или по `Alt+Shift+O` |

## Что нового в 1.3.1

- **[Merge requests](#фича-merge-requests)** — пока в MR есть конфликты с целевой веткой, кнопка
  **Отправить на ревью** неактивна; разрешили конфликты — кнопка снова активна без перезагрузки.
- **[Релизы Jira](#фича-релизы-jira)** — числа на чипах, «Показано N из M» и **Скопировать задачи** считаются
  по всем задачам релиза, а не только по строкам, уже догруженным в список.
- Обязательные метки в настройках «Релизов Jira» редактируются чипами, а не строкой через запятую.

## Что нового в 1.3.0

**Новые фичи**

- **[Релизы Jira](#фича-релизы-jira)** — помощники на странице релиза Jira Cloud (Releases → версия):
  - фильтр по меткам над списком задач: чипы меток с числом задач, «без меток», «без обязательных меток»
    (список обязательных — в настройках);
  - клик по чипу — показать задачи с меткой, Shift+клик — скрыть; несколько меток — «любая» (ИЛИ) или «все» (И);
  - все метки задачи прямо в строке списка, по алфавиту; клик по метке тоже фильтрует;
  - кнопка **Посмотреть MR** справа от статуса задачи — MR из поля задачи, в новой вкладке;
  - **Скопировать задачи (N)** — задачи под фильтром как `KEY — название`, в том числе ещё не догруженные в список;
  - **Открыть в поиске** — тот же отбор в поиске Jira (JQL).
- **[Переходы](#фича-переходы)** — переход с текущей страницы на связанную по правилам «шаблон страницы → ссылка»:
  из контекстного меню или по `Alt+Shift+O`. Доступ к сайтам не нужен.
- **[Импорт и экспорт настроек](#импорт-и-экспорт-настроек)** — все настройки всех фич одним JSON:
  файлом или через буфер обмена, полная копия или «для команды» (без личного username), превью перед импортом.
  Формат версионирован: файлы старых версий будут импортироваться и дальше.

**После обновления**

- «Релизы Jira» — отдельная фича со своим блоком «Сайты»: добавьте туда адрес Jira, даже если он уже есть
  в «Задачах Jira» (доступ к сайту повторно не запрашивается).
- Новые разрешения — `contextMenus` и `activeTab` (для «Переходов»). Предупреждений при установке у них нет,
  повторного подтверждения обновление не требует.
- Политика конфиденциальности обновлена: на странице релиза расширение запрашивает у того же сайта Jira
  метки, статус и поле MR задач релиза.

## Установка

Из Chrome Web Store: [Dev Helper](https://chromewebstore.google.com/detail/dev-helper/ajiokoleamdkgllgakjmomfcajjeipcn).
После установки — шаги 3–4 ниже.

Из исходников:

1. `chrome://extensions` → включить **Режим разработчика**.
2. **Загрузить распакованное расширение** → выбрать папку с расширением (корень репозитория, где лежит `manifest.json`).
3. Кликнуть по иконке расширения (или «Детали» → «Параметры расширения») — откроются настройки.
   Слева список фич, у каждой фичи свой раздел.
4. В разделе фичи, в блоке **Сайты**, добавить адрес — например, `gitlab.com` или адрес своего GitLab.
   Chrome спросит разрешение на доступ к сайту. Без добавленного сайта фича нигде не работает.

### Доступ к сайтам

Расширение не просит доступ ко всем сайтам при установке (`optional_host_permissions`).
Доступ выдаётся по одному сайту из блока «Сайты» в разделе фичи: адрес можно ввести как угодно
(`https://gitlab.example.com/group`, `gitlab.example.com:8443`) — берётся только хост, порт не учитывается.
Background регистрирует content script фичи (`chrome.scripting.registerContentScripts`) только на тех её сайтах,
к которым есть доступ, и перерегистрирует при изменении списка или разрешений — в том числе когда доступ
отзывают в `chrome://extensions`. Такой сайт в настройках помечается «нет доступа» с кнопкой «Разрешить».
Удаление сайта из списка отзывает доступ, если сайт не нужен другим фичам.

После добавления сайта уже открытые вкладки нужно обновить. После установки, а также после обновления,
если ни один сайт не добавлен, страница настроек открывается сама.

После `git pull` — кнопка ↻ на карточке расширения в `chrome://extensions`.

## Публикация в Chrome Web Store

1. Поднять `version` в `manifest.json`.
2. `./scripts/build.sh` — собирает `dist/dev-helper-<version>.zip` только из файлов расширения
   и проверяет, что всё, на что ссылается манифест, на месте.
3. Загрузить zip в Developer Dashboard. Тексты карточки, обоснования разрешений и ответы про данные —
   в [`store/listing.md`](store/listing.md), политика конфиденциальности — [`PRIVACY.md`](PRIVACY.md).

## Фича: Merge requests

На странице merge request под строкой «X requested to merge … into …», над вкладками,
появляется кнопка в стиле GitLab UI. Её название показывает, что произойдёт по клику:

| Название | Когда |
| --- | --- |
| **Отправить на ревью** | открытие Telegram включено и для проекта MR нашёлся топик |
| **Скопировать ссылку на MR** | открытие Telegram выключено или топик для проекта не настроен |

Подсказка при наведении уточняет действие. Если навести курсор и зажать Shift, название
переключается на то, что сделает Shift+клик.

Пока MR в статусе Draft, кнопка неактивна (подсказка: «MR в статусе Draft — снимите его, чтобы
отправить на ревью»). Как только статус снимают («Mark as ready»), кнопка становится активной
без перезагрузки страницы.

Если в MR есть конфликты с целевой веткой, в ряду кнопок появляется предупреждение
**Есть конфликты**, а кнопка становится неактивной (подсказка: «В MR конфликты с целевой веткой —
разрешите их перед отправкой на ревью»). Как только конфликты разрешены, кнопка снова активна
без перезагрузки страницы. Предупреждение показывается на любом MR, фильтр «Мой username в GitLab» на него не влияет. Конфликт определяется по кнопке GitLab «Resolve conflicts» в виджете MR
(появляется и пропадает сразу) и по полю `has_conflicts` из `widget.json` MR — он запрашивается
не чаще раза в минуту и при возврате на вкладку, так что конфликт виден и без прав на push.

Если разметка шапки не распознана, кнопка становится плавающей в правом нижнем углу.
Когда шапка MR прилипает к верху при прокрутке, ряд с кнопкой скрывается.

По клику в буфер обмена кладётся

```
Название merge request

https://gitlab.example.com/group/project/-/merge_requests/123
```

и (опционально) открывается заданный топик в Telegram.

Название кладётся в буфер жирным: в клипборд пишутся оба флейвора — `text/html`
(`<b>Название</b>`, его подхватывают Telegram Desktop и Web) и `text/plain` (обычный текст
для полей без форматирования). Отключается галочкой в настройках.

### Шаблон текста

Формат копируемого текста настраивается. По умолчанию `{title}\n\n{url}`.

| Плейсхолдер | Значение |
| --- | --- |
| `{title}` | название MR (кладётся жирным, если включено) |
| `{url}` | канонический URL merge request |
| `{iid}` | номер MR |
| `{project}` | путь проекта, например `group/subgroup/project` |
| `{branch}` | исходная ветка — только при копировании со страницы MR |
| `{author}` | автор MR — только при копировании со страницы MR |

Неизвестные плейсхолдеры остаются как есть, пустые строки схлопываются.
Пример: `🔍 Ревью: {title}\n{branch}\n{url}`.

### Горячая клавиша

`Alt+Shift+C` на странице MR копирует то же, что и кнопка. Комбинацию можно переназначить
в `chrome://extensions/shortcuts`. Отключается галочкой в настройках. На Draft-MR не срабатывает.

### Настройки

Раздел «Merge requests» на странице настроек. Переключатель «Включено» отключает фичу целиком.

- **Сайты → Адреса GitLab** — gitlab.com и/или адреса self-hosted GitLab, см. [Доступ к сайтам](#доступ-к-сайтам).
  Сохраняются сразу, без кнопки «Сохранить».

- **Шаблон копируемого текста** — см. выше.
- **Мой username в GitLab** — если указан, кнопка на странице MR, кнопки в списке и горячая клавиша
  работают только на MR, где вы автор. Автор берётся из `data-username` ссылки на автора;
  если его не удалось определить, кнопка показывается. Несколько username — через запятую.
- **Название жирным** — класть в буфер форматированный вариант (`text/html`) рядом с обычным.
- **Открывать Telegram после копирования** — включает переход в топик.
- **Открывать сразу в приложении** — ссылка `t.me` переводится в `tg://` (`tg://privatepost?channel=…&post=…`
  или `tg://resolve?domain=…&post=…`), и браузер сразу предлагает открыть Telegram Desktop, минуя
  страницу t.me с кнопкой «Open message». Без галочки ссылка открывается в новой вкладке как есть.
- **Ссылка на топик по умолчанию** — используется, если проект не подошёл ни под одно правило.
- **Топики по проектам** — пары «путь проекта → ссылка на топик».
  Вложенные подгруппы поддерживаются на любую глубину: для MR в
  `gitlab.example.com/group/sub/subsub/project` сработает правило `group`, `sub/subsub`,
  `group/sub/subsub/project` или `gitlab.example.com/group`.
  Сравнение по сегментам пути, поэтому `billing` не совпадёт с `billing-legacy`;
  внутри сегмента можно использовать `*` (`group/*/api`).
  Выигрывает самое вложенное (длинное) правило.
- **Кнопка «Открыть задачу в Jira»**, **URL Jira по умолчанию**, **Jira по проектам** — см. раздел выше.
- **Минимум апрувов** — см. [Апрув MR](#апрув-mr).
- **Кнопка «Создать MR на stage»**, **Ветка stage по умолчанию**, **Ветка stage по проектам** —
  см. [Создать MR на stage](#создать-mr-на-stage).
- **Кнопки префиксов**, **Префиксы**, **Префикс жирным** — см. [Префиксы комментариев](#префиксы-комментариев).

Ссылку на топик берут в Telegram: правый клик по топику → «Копировать ссылку».
Формат `https://t.me/c/<chat_id>/<topic_id>` (приватная группа) или `https://t.me/<username>/<topic_id>`.

### Список merge requests

В списках MR (проектных, групповых и на `/dashboard/merge_requests`) рядом с названием каждой
MR появляется иконка копирования — копирует то же самое, без открытия самой MR.
Топик в Telegram резолвится по проекту той MR, на которую нажали, а не по текущей странице,
поэтому в групповом списке и дашборде правила работают корректно.
У Draft-MR иконка неактивна.
Отключается галочкой в настройках.

### Префиксы комментариев

Отдельным рядом над кнопками формы комментария (**Start a review** / **Add comment now** / **Cancel**) — кнопка
на каждый префикс из настроек (например `blocking`, `question`, `nit`; по умолчанию список пуст — ряда нет).
Работает во всех формах на странице MR: комментарий к строке диффа, ответ в треде, общий комментарий, правка своего комментария.

- Клик ставит префикс в начало комментария: `**nit:** ` (или `nit: ` без галочки «жирным»).
  Если в начале уже стоит другой префикс из списка, он заменяется; повторный клик по тому же — убирает.
  Префикс, который уже стоит в комментарии, подсвечен заливкой.
- Кнопки — в стиле GitLab (`gl-button`). Цвет префикса задаётся в настройках: контур и текст кнопки этого цвета
  (как у **Add comment now**), применённый префикс — заливка (как у **Start a review**). Без цвета — обычная серая кнопка.
- Оба режима редактора: в plain text вставляется markdown, в rich text — текст, а жирный включается
  горячей клавишей самого редактора (Ctrl/Cmd+B).
  Правка попадает в историю, Ctrl+Z её отменяет.
- Показывается на всех MR, фильтр «Мой username в GitLab» на него не влияет. Отключается галочкой в настройках.

### Открыть задачу в Jira

Рядом с «Отправить на ревью» в шапке MR — ссылка-кнопка **Открыть задачу в Jira**
(открывается в новой вкладке, работает средний клик).

- Ключ задачи (`PROJ-123`) ищется сначала в исходной ветке (`feature/PROJ-123-add-foo`), затем в названии MR.
  Учитываются только заглавные ключи, как в Jira: `release-1` или `proj-12` задачей не считаются.
- URL Jira берётся из правил **Jira по проектам** — сопоставление такое же, как у топиков
  (сегменты пути, `*`, необязательный хост, выигрывает самое вложенное правило); иначе — **URL Jira по умолчанию**.
  Ссылка строится как `<URL>/browse/<ключ>`; хвост `/browse` в URL можно не убирать.
- Если ключ не найден или Jira для проекта не настроена — кнопка неактивна, причина в подсказке.
- Показывается на всех MR, фильтр «Мой username в GitLab» на неё не влияет. Отключается галочкой в настройках.

### Апрув MR

MR считается **апрувнутым**, когда апрувов не меньше **Минимума апрувов** (по умолчанию 2) и нет нерешённых тредов.
Апрувнутый MR гасит «Отправить на ревью» и открывает «Создать MR на stage».

Всё определяется по DOM страницы MR, запросов к GitLab нет:

- апрувы — число аватаров в сводке виджета апрувов (`[data-testid="approvals-summary-content"]`);
- нерешённые треды — число из счётчика тредов в шапке MR (`.discussions-counter`):
  «3 open threads» (в старых версиях «3 unresolved threads»), «All threads resolved!» или совсем старое
  «2/5 threads resolved», на любом языке интерфейса. Счётчика нет, когда в MR нет resolvable-тредов, —
  тогда нерешённых 0, если обсуждения уже загружены.

Виджет апрувов есть только на вкладке Overview. Последние увиденные значения запоминаются, поэтому после
Overview состояние известно и на Changes / Commits; если MR открыт сразу на другой вкладке — MR не считается
апрувнутым, а у «Создать MR на stage» в подсказке просьба открыть Overview.

### Создать MR на stage

Последней в ряду кнопок шапки MR — ссылка-кнопка **Создать MR на stage**. Открывает в новой вкладке форму
нового MR с заполненными исходной веткой (ветка текущего MR) и целевой (stage); создаёт MR сам пользователь.

- Кнопка активна, когда MR не Draft, без конфликтов (определяется так же, как для «Отправить на ревью»)
  и [апрувнут](#апрув-mr). Иначе кнопка неактивна, в подсказке перечислено, что мешает
  («апрувов 1 из 2, нерешённых тредов: 3»).
- Ветки берутся из строки «requested to merge X into Y». Имя ветки stage — из правил **Ветка stage по проектам**
  (сопоставление как у топиков), иначе — **Ветка stage по умолчанию** (`stage`). Название кнопки — с этим именем.
- На MR, который сам нацелен в stage, кнопки нет. На MR из форка (исходная ветка вида `namespace/project:branch`) — неактивна.
- Показывается на всех MR, фильтр «Мой username в GitLab» на неё не влияет. Отключается галочкой в настройках.

### Переход из Jira («Залить на stage»)

Кнопка [«Залить на stage»](#фича-задачи-jira) в Jira открывает MR с меткой `#dev-helper-stage`.
На странице MR метка сразу убирается из адреса (обновление страницы не повторит переход), затем:

- пока апрувы и треды не прочитаны со страницы — ждём, до 20 секунд;
- условия «Создать MR на stage» выполнены и не меняются 1,5 секунды (виджет MR дорисовывается частями,
  конфликты могут появиться позже апрувов) — в этой же вкладке открывается форма нового MR на stage;
- иначе в ряду кнопок шапки MR — «Залить на stage нельзя: …» с причинами
  (в том числе «MR и так нацелен в stage», «MR из форка»).

Работает, даже если кнопка «Создать MR на stage» выключена в настройках — нужна только включённая фича.

### Переход из Jira («Pipeline ветки»)

Кнопка [«Pipeline ветки»](#фича-задачи-jira) в Jira открывает MR с меткой `#dev-helper-pipeline`
(в задаче есть только ссылка на MR, исходную ветку знает шапка MR). На странице MR метка сразу убирается из адреса,
затем, как только в шапке появилась исходная ветка (ждём до 10 секунд), в этой же вкладке открывается
`/<проект>/-/pipelines/<ветка>/latest` — последний pipeline ветки, где вручную запускают preview-окружение.
Если у ветки ещё нет pipeline, GitLab покажет 404.

Не получилось — в ряду кнопок шапки MR «Открыть pipeline ветки нельзя: …»
(«не удалось определить исходную ветку MR», «MR из форка»).

### Поведение кнопки

- Клик — копирует текст и, если включено, открывает Telegram.
- **Shift+клик** — инвертирует настройку открытия Telegram (быстро скопировать без перехода, или наоборот).
- **Draft** — кнопка неактивна, клик и горячая клавиша ничего не делают.
- **MR апрувнут** ([апрув MR](#апрув-mr)) — кнопка неактивна в состоянии success: зелёная галочка
  и надпись «MR апрувнут», клик и горячая клавиша ничего не делают. Только на странице MR — в списке апрувов в разметке нет.
- **Конфликты** — кнопка неактивна, рядом с ней предупреждение «Есть конфликты»; клик и горячая клавиша
  ничего не делают. Draft и «MR апрувнут» важнее: при них показывается их состояние.

### Как берётся название и ссылка

- Название — из заголовка MR (`[data-testid="title-content"]`, `h1.title` и др.), фолбэк — `document.title`;
  суффикс `(!123)` отрезается.
- Статус Draft — по префиксу названия, как в самом GitLab: `Draft:`, `[Draft]`, `(Draft)`, `Draft - `,
  а также устаревшие `WIP:`, `[WIP]`, `(WIP)`, без учёта регистра. Изменение названия отслеживается
  на лету (в том числе правка текстового узла, которую делает Vue после «Mark as ready»).
- Ссылка — канонический URL MR: адрес обрезается до `/-/merge_requests/<iid>`,
  поэтому с вкладок `/diffs`, `/commits` и с любыми query-параметрами копируется чистая ссылка.
- Путь проекта берётся целиком до `/-/`, так что вложенные подгруппы любой глубины
  (и установка GitLab на подпути) обрабатываются корректно.

## Фича: Задачи Jira

Подсвеченный блок с кнопками **Залить на stage** и **Pipeline ветки** под рядом кнопок со статусом задачи
в Jira Cloud — и на странице задачи (`/browse/KEY`), и в модальном окне на досках, в бэклоге и поиске.
Рядом с кнопками — какой MR будет открыт (`group/project!12`) или что мешает. Блок показывается,
если в задаче нужна хотя бы одна из кнопок.

- **Залить на stage** — только в статусе **Тестирование** (настраивается, без учёта регистра).
- **Pipeline ветки** — в любом статусе, если у задачи есть хотя бы одна из меток из настроек
  (через запятую или пробел, без учёта регистра; пусто — кнопки нет). Метки читаются из поля **Labels**
  (название настраивается): тексты чипов поля. Поле должно быть видно в задаче, а не свёрнуто в «More fields».
  Кнопка открывает MR в новой вкладке с меткой `#dev-helper-pipeline`, дальше —
  [переход из Jira](#переход-из-jira-pipeline-ветки) на стороне GitLab.
- Берёт ссылку на MR из поля **Merge Request** (название поля настраивается): из ссылок поля и из текста.
  Хвост `/diffs`, `#note_…` отрезается.
- Ровно одна ссылка — «Залить на stage» открывает MR в новой вкладке с меткой `#dev-helper-stage`,
  дальше — [переход из Jira](#переход-из-jira-залить-на-stage) на стороне GitLab.
- Нет поля, нет ссылки или ссылок несколько — кнопки неактивны, причина написана рядом;
  несколько MR подсвечиваются как ошибка.

Нужны адрес Jira в блоке «Сайты» этой фичи и адрес GitLab в блоке «Сайты» фичи «Merge requests».

Разметка — Jira Cloud: статус — `[data-testid="ref-spotlight-target-status-spotlight"]`
(текст — `…status-button--text`, фолбэк — `aria-label` «<статус> - Change status»),
заголовки полей — `[data-component-selector="jira-issue-field-heading-field-heading-title"]`.
Поле ищется в той же задаче, что и статус; строка поля — самый широкий предок заголовка без заголовков других полей.
Блок встаёт после ряда со статусом — ближайшего предка статуса, который горизонтальный flex с несколькими детьми.

## Фича: Релизы Jira

На странице релиза Jira Cloud (Releases → версия, адрес с `/versions/<id>`) над списком **Work items** —
панель с чипами меток задач релиза и числом задач у каждой; рядом — «Показано N из M».
Счётчик Jira «Work items» при этом не меняется. Выбор сбрасывается при переходе на другой релиз.

Числа на чипах, «Показано N из M» и копирование считаются по **всем** задачам релиза из API, а не по строкам
на странице: Jira показывает список частями. Пока в списке не все задачи, в панели —
«в списке пока K из M»; фильтр скрывает показанные строки и подхватывает догруженные.

- **Клик** по чипу — показать задачи с меткой, **Shift+клик** — скрыть задачи с ней (чип зачёркнут);
  повторный такой же клик снимает выбор, «Сбросить» — снять всё.
- Исключённые метки скрывают задачу всегда. Из выбранных нужна хотя бы одна — **любая из выбранных (ИЛИ)**;
  при двух и больше выбранных появляется переключатель на **все выбранные (И)**.

- **без меток** — задачи без единой метки.
- **без обязательных меток** — задачи, у которых нет ни одной метки из настройки **Обязательные метки**
  (без учёта регистра; пусто — чипа нет). Обязательные метки в чипах выделены. В настройках метки
  редактируются чипами: Enter, запятая или пробел — добавить (можно вставить список целиком),
  ✕ или Backspace в пустом поле — убрать; повторы не добавляются.
- Служебные чипы показываются и с нулём — значит, все задачи размечены.
- **Метки в строках** — в каждой строке списка сразу после названия задачи все её метки по алфавиту,
  без сокращения: блок меток не сжимается, при нехватке места сокращается название. Обязательные выделены.
  Отключается в настройках («Метки в списке»). Название — листовой элемент строки с самым длинным текстом.
  Клик по метке в строке работает как клик по её чипу (Shift — исключить); задача при этом не открывается.
- **MR в строках** — справа от статуса задачи кнопка **Посмотреть MR** на MR из поля задачи
  **Merge Request** (название настраивается, без учёта регистра); несколько MR — кнопка на каждый с номером
  (`Посмотреть MR !12`), какой это MR — в подсказке. Хвост `/diffs`, `#note_…` отрезается.
  Кнопка — ссылка: открывает MR в новой вкладке, а не задачу; работает средний клик.
  Статус в строке ищется по названию статуса задачи из API (последний элемент строки с этим текстом,
  поднятый до обёртки-лозенджа); не нашёлся — кнопки встают отдельной строкой под метками
  (строки Jira фиксированной высоты, так что это только запасной вариант). Поле может быть текстовым, URL или с форматированием —
  ссылки ищутся во всём значении. Нет поля с таким названием — причина в строке панели.
  Отключается в настройках («MR в списке»).
- **Скопировать задачи (N)** — все задачи релиза под фильтром, по строке на задачу: `KEY — название`
  (в HTML ключ — ссылка на задачу). Сначала — в порядке списка, затем ещё не догруженные по ключу;
  название берётся из API. Для релиз-заметок и QA.
- **Открыть в поиске** — тот же отбор в поиске Jira (`/issues/?jql=…`), где видны все задачи и колонки:
  `fixVersion = <id>`, выбранные метки через `OR` / `AND`, исключённые — `labels is EMPTY OR labels not in (…)`
  (иначе JQL теряет задачи без меток). Для «без обязательных» к меткам из настроек добавляются
  их написания из задач релиза — в JQL метки сравниваются как есть.

Как устроено:

- В строках списка меток и MR нет, поэтому они берутся запросом
  `GET /rest/api/3/search/jql?jql=fixVersion = <id>&fields=labels,summary,status,<поле MR>` к тому же сайту под сессией
  пользователя (только чтение, номер версии — только цифры из адреса). id поля MR (`customfield_…`)
  находится по названию через `GET /rest/api/3/field`; смена поля или включение ссылок перезапрашивает данные.
- Строка задачи — самый высокий предок ключа задачи (ссылка `/browse/KEY` или текст ключа), в котором нет
  ключей других задач релиза; скрывается атрибутом `data-dhr-hidden` (className строк React перезаписывает).
- Если в списке появилась ссылка на задачу, которой не было в ответе (добавили в релиз), метки
  перезапрашиваются — не чаще раза в 10 секунд и один раз на ключ.
- Jira — SPA, на релиз переходят без перезагрузки, поэтому скрипт загружается на страницах Jira
  (`/browse/*`, `/jira/*`, `/issues*`, `/projects/*`) и сам проверяет адрес.

Нужен адрес Jira в блоке «Сайты» этой фичи.

## Фича: Переходы

Переход с текущей страницы на связанную: части адреса (id, slug, окружение) подставляются в ссылку
по правилам. Например, с товара на сайте — в админку, со stage — на prod. Доступ к сайтам не нужен,
блока «Сайты» у фичи нет: адрес страницы или ссылки Chrome передаёт в событии контекстного меню,
а горячая клавиша выдаёт `activeTab`. Content script нет — всё делает background.

Правило — название, шаблон страницы и ссылка:

```
Открыть в админке   {env}.example.com/product/*-{id:num}   →   https://{env}-admin.example.com/products/{id}
На prod             stage.example.com/product/{slug}       →   https://example.com/product/{slug}
```

- Шаблон страницы — хост (с портом, если он есть в адресе) и путь; схема и `/` в конце не важны.
  Сравнивается с `host + pathname` без учёта регистра, query и hash отбрасываются.
  - `{имя}` — сегмент пути, в хосте — часть до точки; `{имя:num}` — число. Имя — латиница, цифры, `_`; каждое один раз.
  - `*` — любые символы внутри сегмента (в хосте — внутри части до точки).
  - Из `stage.example.com/product/brake-pad-c7011lr-512644?from=catalog` первое правило берёт
    `env = stage` и `id = 512644`: `*` откатывается до последнего дефиса перед числом в конце.
- Ссылка — `http(s)://…`; `{имя}` заменяется значением, переменные должны быть в шаблоне страницы.
- Название — текст пункта меню; пусто — «Открыть &lt;хост ссылки&gt;».
- `example.com` под `{env}.example.com` не подходит — для адреса без поддомена нужно отдельное правило.
- Кривой шаблон или ссылка подсвечиваются в настройках, такое правило не применяется.
- В настройках есть поле «Проверка»: вставленный адрес сразу показывает все ссылки по текущим (ещё не сохранённым) правилам.

Запуск (оба способа включаются в настройках отдельно):

- **Контекстное меню** — пункт на каждое правило, на странице, подходящей под его шаблон, и на ссылках
  на такие страницы (карточки в каталоге). Несколько пунктов Chrome собирает в подменю «Dev Helper».
  Видимость задаётся `documentUrlPatterns` / `targetUrlPatterns` из шаблона; match pattern шире правила
  (`*` захватывает `/`, переменная в первой части хоста — `*.домен`, включая сам домен), поэтому пункт
  иногда виден там, где правило не подойдёт, — тогда клик ничего не открывает. Меню пересоздаётся при изменении настроек.
- **Горячая клавиша** `Alt+Shift+O` (команда `open-redirect`, переназначается в `chrome://extensions/shortcuts`) —
  по первому подходящему правилу. Если ни одно не подошло, ничего не происходит.

Ссылка открывается в новой вкладке рядом с текущей.

## Импорт и экспорт настроек

Раздел **Импорт и экспорт** в меню настроек (под фичами).

- **Экспорт** — «Скачать файл» (`dev-helper-settings-<дата>.json`) или «Скопировать в буфер».
  - **Полная копия** — все настройки всех фич, включая сайты и личные: резервная копия, другой браузер или профиль.
  - **Для команды** — без личных настроек (`personal` фичи; сейчас это username в GitLab), чтобы поделиться правилами.
- **Импорт** — файл, ссылка или вставленный текст. Сначала превью: по каждой фиче, какие настройки изменятся и что
  пропущено и почему; фичи выбираются галочками. Запись — только по «Применить», одним вызовом
  `chrome.storage.sync.set` (либо всё, либо ничего); открытые страницы подхватывают изменения сами.
  - Настройки, которых нет в файле, не меняются — файл «для команды» не сотрёт ваш username.
  - «Дополнять списки» — правила и сайты из файла добавляются к своим (без повторов), а не заменяют их.
  - Новые сайты: Chrome один раз спросит доступ ко всем сразу; отказались — сайты останутся в списке
    с «нет доступа» и кнопкой «Разрешить».
- **Загрузка по ссылке** — общий файл команды, например экспорт «для команды» в репозитории:
  `https://gitlab.example.com/group/repo/-/raw/main/dev-helper.json`. Дальше — то же превью и «Применить».
  - Ссылки `http` и `https`; без схемы — `https`. Ссылка на просмотр файла в GitLab (`/-/blob/`) сама
    переводится в raw (`/-/raw/`).
  - По «Загрузить» Chrome спросит доступ к сайту файла (без него запрос не пройдёт). Запрос идёт с куками сайта:
    приватный файл GitLab загрузится, если вы вошли в GitLab в этом браузере.
  - Ссылка запоминается после «Применить» (ключ `backup.source` в `chrome.storage.sync`, в экспорт не попадает) —
    чтобы подтянуть новую версию файла, достаточно нажать «Загрузить» ещё раз. Автоматически настройки
    не обновляются: запись — только после превью.
  - Ошибки — понятным текстом: нет доступа (401/403), файл не найден (404, в том числе приватный без входа),
    вместо файла пришла HTML-страница (страница входа или ссылка не на raw), файл больше 256 КБ, таймаут 15 секунд.

### Формат и совместимость

```json
{
  "app": "dev-helper",
  "format": 1,
  "kind": "full",
  "extensionVersion": "1.3.0",
  "exportedAt": "2026-10-15T10:00:00.000Z",
  "features": {
    "jiraRelease": { "version": 1, "settings": { "enabled": true, "requiredLabels": "back, front" } }
  }
}
```

- `app` — чужой JSON не примем. `format` — версия конверта: растёт, только если меняется сама структура файла;
  файл с `format` новее, чем знает расширение, отклоняется с просьбой обновить расширение.
  `kind`, `extensionVersion`, `exportedAt` — справочно, на импорт не влияют.
- `features.<id>.settings` — имена те же, что ключи `chrome.storage.sync` (`<id фичи>.<настройка>`),
  отдельного слоя имён нет. Пишутся все значения, а не только отличные от умолчаний: если умолчания сменятся,
  файл сохранит ваш выбор.
- **Старый файл в новом расширении** импортируется всегда. Новых настроек в нём нет — они не трогаются.
  Если настройку переименовали или поменяли её смысл, фича поднимает `settingsVersion` и задаёт
  `migrate(settings, fromVersion)` — старые файлы приводятся к новому виду при импорте.
- **Новый файл в старом расширении** импортируется по возможности: неизвестные фичи и настройки, значения
  другого типа (сверка с типом из `defaults`) пропускаются и показываются в превью.
- Значения больше лимита `chrome.storage.sync` (8 КБ на настройку) пропускаются с объяснением.
- Сайты нормализуются как при ручном добавлении: только хост, мусор отбрасывается.

(content scripts одного расширения делят общий изолированный мир).

Настройки хранятся ключами вида `<id фичи>.<настройка>`, например `mergeRequests.rules`.
Настройки версии без фич (`template`, `rules`, …) переносятся под префикс автоматически
при обновлении расширения.

## Как добавить фичу

1. `features/<slug>/feature.js` — `DevHelper.registerFeature({ id, slug, title, description, content, defaults })`;
   в `defaults` обязательно `enabled`. Если фича работает на страницах сайтов — `content`:
   `paths` (пути страниц в формате match pattern, например `/*/-/merge_requests*`), `js` (сначала нужные
   `common/*.js`, затем `feature.js` и `content.js`), `css`, подписи `sitesLabel` и `sitesPlaceholder`;
   в `defaults` — `hosts: []`. Блок «Сайты» в настройках и регистрация скрипта появятся сами.
2. `features/<slug>/options.html` — фрагмент раздела настроек. Поля с атрибутом
   `data-field="<настройка>"` (checkbox, input, textarea) загружаются и сохраняются сами.
3. При необходимости `features/<slug>/options.js` — `registerFeature({ id, options: { init, load, collect } })`
   для нестандартных полей (как списки правил у Merge requests).
4. `features/<slug>/content.js` — логика на странице; настройки через
   `DevHelper.storage.getFeature(id, defaults)` и `onFeatureChanged`, уважать `enabled`.
5. Подключить:
   - в `options/options.html` — `feature.js` и `options.js` фичи;
   - в `background.js` — `feature.js` в `importScripts` (нужен для регистрации content script,
     переноса настроек и дефолтов).
6. Импорт и экспорт подхватят фичу сами — по `defaults`. Личные настройки (username и т. п.) — в `personal`,
   никогда не экспортируемые — в `exportExclude`. Переименовали настройку или поменяли её смысл —
   поднять `settingsVersion` и добавить `migrate(settings, fromVersion)`, чтобы старые файлы импортировались.
7. Горячие клавиши — в `manifest.json` → `commands`; background пересылает во вкладку
   `{ type: 'command', command }`, фича слушает свою команду.

Работает и с gitlab.com, и с self-hosted GitLab — домен не зашит, адреса задаются в блоке «Сайты».
